Build a Go backend for a Smart Biometric Attendance & Institutional Identity 
Platform (SparkLab Africa / Juldtech Solutions). Single Go binary serving both 
a REST API (for fingerprint/RFID devices) and a server-rendered web dashboard 
(for admins), backed by SQLite.

STACK
- Go + Gin (routing/middleware)
- SQLite via modernc.org/sqlite or mattn/go-sqlite3
- sqlc or plain database/sql with migrations (golang-migrate)
- html/template or htmx for the dashboard (keep it simple, server-rendered — 
  no separate frontend build step for MVP)
- JWT for admin session auth; API keys (hashed) for device auth

PROJECT STRUCTURE
/cmd/server/main.go
/internal/db/            — migrations, queries
/internal/models/        — structs matching schema
/internal/handlers/      — split by domain: auth, users, devices, attendance, 
                            sms, dashboard, rfid
/internal/middleware/    — auth (JWT for admins, API key for devices), 
                            org-scoping, rate limiting
/internal/services/      — attendance rules engine, SMS sender, sync logic
/web/templates/          — dashboard HTML templates
/web/static/             — CSS/JS assets

DATA MODEL (SQLite)
Implement these tables (see attached ERD): organizations, branches, users, 
devices, device_enrollments (user_id, device_id, slot_id, status, enrolled_at 
— no biometric data, just the mapping), rfid_cards (uid, issue_date, 
expiry_date nullable, status, personalization_status, replacement history via 
a separate rfid_card_history table), attendance_events, attendance_rules, 
sms_logs, audit_logs, roles/permissions. Every table except organizations has 
organization_id for multi-tenant isolation — enforce this at the query layer, 
not just via a WHERE clause the caller might forget.

Also add: device_commands (id, device_id FK, command_type, payload_json, 
status: pending/delivered/acked, created_at) — this is the queue devices poll 
for backend-to-device commands (enroll, delete, sync, restart, etc), since 
we're using plain REST polling, not MQTT.

DEVICE-FACING API (REST, polled by hardware — auth via device API key)
POST   /api/v1/devices/register          — device self-registers, gets API key
POST   /api/v1/devices/:id/heartbeat      — updates last_heartbeat, online status
GET    /api/v1/devices/:id/commands       — fetch pending commands (enroll, 
                                             delete, sync, restart, lock)
POST   /api/v1/devices/:id/commands/:cmdId/ack — mark command delivered/done
POST   /api/v1/attendance                 — single event: 
                                             {device_id, user_id, event, 
                                              timestamp, method}
POST   /api/v1/attendance/batch           — bulk sync after offline period, 
                                             dedupe by (user_id, device_id, 
                                             timestamp, event)

ADMIN/DASHBOARD API + WEB (JWT auth, org-scoped)
POST   /auth/login, /auth/logout, /auth/refresh
CRUD   /users                             — includes fingerprint_status, 
                                             RFID card assignment
CRUD   /devices                           — register, view status/heartbeat
CRUD   /rfid-cards                        — issue, personalize, 
                                             activate/deactivate, replace
GET    /attendance                        — filterable (user, date, branch, 
                                             device, status)
POST   /attendance/:id/correct            — manual correction, flagged in 
                                             audit_logs
GET    /reports/daily|weekly|monthly      — PDF/Excel/CSV export
POST   /sms/templates, GET /sms/history
GET    /dashboard                         — today's summary (present/absent/
                                             late/clocked-out counts)
GET    /devices/status                    — online/offline table

WEB DASHBOARD PAGES (server-rendered)
- Login
- Dashboard (today's attendance summary, device status, recent events)
- Users (list/create/edit, fingerprint status, RFID card link)
- Devices (status, last heartbeat, pending commands)
- RFID Cards (issue/personalize/manage lifecycle)
- Attendance (searchable table, manual correction)
- Reports (generate + export)
- Settings (attendance rules per org, SMS templates)

CORE LOGIC TO IMPLEMENT
1. Attendance rules engine — configurable per-org working hours, late 
   threshold, early departure threshold (jsonb-like in a rules table); apply 
   on event ingestion to tag late/early/on-time.
2. Offline dedup — attendance/batch must not create duplicate events for 
   the same (user, device, timestamp).
3. Org-level data isolation — middleware that injects organization_id from 
   the authenticated admin/device context into every query; write a test 
   that confirms cross-org queries return nothing.
4. SMS dispatch — on clock-in/out/late/absence, queue an SMS job (don't 
   block the request); simple in-process worker goroutine + a jobs table is 
   fine for MVP (no external queue needed yet).
5. RBAC — roles: super_admin, org_admin, hr_admin, school_admin, teacher, 
   church_leader, parent_guardian, viewer — each scoped to org/branch/
   class/ministry as applicable.
6. Audit logging — wrap all mutating admin actions (user CRUD, attendance 
   correction, device config change) to write to audit_logs with 
   before/after values.

NON-GOALS FOR THIS PASS
- No MQTT — REST polling only.
- No mobile app, no payments/billing, no AI analytics — these are Phase 2/3.
- Don't build fingerprint matching logic — that lives entirely on the 
  hardware device; the backend only receives resolved user_id + event.
